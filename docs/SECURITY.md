# Security

## Authentication

| Concern | Implementation |
| --- | --- |
| Password storage | scrypt, N=16384, r=8, p=1, 16-byte random salt, stored as `scrypt$N$r$p$salt$hash`. Verification uses `crypto.timingSafeEqual`. |
| Password policy | ≥10 characters, at least one letter and one digit, ≤200 characters. |
| Sessions | 256-bit opaque token from `crypto.randomBytes`; only its SHA-256 digest is stored. Cookie `folio_session` is `HttpOnly`, `SameSite=Lax`, `Secure` in production, `Path=/`, 14-day TTL. |
| Session invalidation | Sign-out deletes the row; password change and password reset delete **all** rows for the user. Expired sessions are pruned on every auth attempt. |
| Password reset | 256-bit token, stored hashed, 30-minute TTL, single use (`used_at`), previous unused tokens deleted on a new request. The response for an unknown address is deliberately identical to a successful request. |
| Account enumeration | Sign-in returns one message for unknown email and wrong password. The reset flow never confirms whether an address exists (except that the development-only reset link is shown only for real accounts — production never reveals it). |
| Rate limits | Sign-in 8 / 15 min per IP+email, sign-up 5 / 15 min per IP, reset request 4 / 15 min per IP, contact form and uploads limited per IP/user, GitHub sync 3 / minute per user. |
| Privilege escalation | Roles are never accepted from the client. `assignableRole()` returns `USER` unconditionally; only the seed (server-side) creates an `OWNER`. |

## Authorization

Checks happen in the server action or page, reading the actor from the session — never from a hidden field, query parameter, or client state.

| Resource | Rule | Enforcement point |
| --- | --- | --- |
| Portfolio edits (profile, appearance, sections, content, projects, slug, publish) | `actor.id === portfolio.userId` **or** `actor.role === "OWNER"` | `authorizedPortfolio()` in `src/app/actions/portfolio.ts`; the same predicate in `wizard.ts` |
| Individual project rows | Must belong to the resolved portfolio (`findFirst({ id, portfolioId })`) | Every project action |
| Contact messages | Recipient or platform owner | `markMessageReadAction`, `deleteMessageAction` |
| GitHub connection + sync | Portfolio owner or platform owner | `syncGithubAction`, `disconnectGithubAction` |
| Dashboard pages | Requires a session | `src/app/dashboard/layout.tsx` → `requireUser()` |
| Admin pages | Requires `role === "OWNER"`; others redirect to `/dashboard?denied=admin` | `src/app/admin/layout.tsx` → `requireOwner()`; every admin page re-checks |
| Public portfolio | Only when `published = true` | `getPublishedPortfolio()`; drafts 404 for everyone, including the owner (previews use the authenticated `/dashboard/preview`) |
| Section visibility | Filtered in the view model before rendering | `toPortfolioView()` — hidden Contact also blanks the email so it cannot leak via the hero or JSON-LD |
| Uploads | Session required, same-origin `Origin` check, per-user rate limit | `src/app/api/uploads/route.ts` |

## Injection and input handling

- All SQL values are passed as parameters (`$1`, `$2`, …). Identifiers come from a static table/column map, so no request value can reach an identifier position. `$queryRaw` is a tagged template only — string concatenation is not exposed.
- Every form payload is parsed with Zod. Unknown keys are dropped by the schema rather than persisted.
- URLs must be `http://` or `https://` (`httpUrlSchema`); `javascript:` and `data:` are rejected on projects, certification and social links.
- Rendered text is escaped by React. A test asserts `<script>` in a headline is escaped.
- Profile images are validated by magic bytes (PNG/JPEG/WebP), SVG is rejected, the filename is generated by the server, and the account id is validated before use in a path.
- The template renderer resolves only the four whitelisted components; an unknown value falls back to `signal`.

## Transport and headers

Set on every response in `next.config.ts`:

- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: SAMEORIGIN`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy: camera=(), microphone=(), geolocation=()`
- `poweredByHeader: false`

**Content Security Policy is not set by the app.** The App Router needs inline bootstrap scripts and the templates set per-portfolio accent colours inline. If your deployment needs a CSP, apply it at the proxy with a per-request nonce, and allow `'unsafe-inline'` for styles only:

```
Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'nonce-<per-request>';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https://avatars.githubusercontent.com https://raw.githubusercontent.com;
  font-src 'self';
  connect-src 'self';
  frame-ancestors 'self';
  base-uri 'none';
  form-action 'self'
```

## CSRF

Server actions are POST requests invoked through Next's action protocol, and the session cookie is `SameSite=Lax`, so cross-site form posts do not carry credentials. The upload route additionally rejects cross-origin `Origin` headers. If you add classic REST mutations, add an explicit double-submit token.

## Secrets

- `GITHUB_TOKEN`, `RESEND_API_KEY` and `DATABASE_URL` are read only in server code. The GitHub token is never serialised into props, responses, or the health endpoint — `/api/health` reports only whether a token is configured (`githubToken: true`).
- `.env` and `.data/` are gitignored; `.env.example` contains placeholders only.
- Password-reset tokens appear in URLs (by design); they are single use, short-lived and hashed at rest.

## Residual risks

1. In-process rate limiting resets on deploy and is per instance — back it with Redis for multi-replica hosting.
2. No 2FA, no email verification, no login notifications.
3. Uploaded images are served from `public/uploads/` without re-encoding. Magic-byte checks block polyglot files, but re-encoding with `sharp` would be stronger.
4. The owner account's password is whatever `SEED_OWNER_PASSWORD` contains. Change it in `/dashboard/settings` before exposing the site.
5. No audit log for admin actions beyond per-portfolio `ActivityLog` entries; add an `admin_actions` table if you need accountability across accounts.

## Reporting

If you find a vulnerability, do not open a public issue. Email the address on the owner's portfolio with reproduction steps; expect an acknowledgement within a few days.
